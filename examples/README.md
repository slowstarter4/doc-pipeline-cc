파이프라인 입력(기획문서)과, 도출 결과를 대볼 정답지를 둔다.

| 파일 | 크기 | 용도 |
|---|---|---|
| `todo_plan.md` | 0.6KB | 최소 예제. 엔티티 1개 |
| `library_plan.md` | 4KB | 엔티티 3개 + 관계 + 업무규칙. 4스택·postgres 검증의 기준 문서 |
| `commerce_qwen_plan.md` | 41KB | 대형 예제. 엔티티 12개 + 상태 전이 + 업무규칙 14개 + 권한 매트릭스 |
| `commerce_qwen_reference.md` | 70KB | **입력이 아니다.** 위 문서의 원본(설계까지 들어간 버전) = 도출 결과 정답지 |

## 기획문서에 뭘 쓰고 뭘 안 쓰나

파이프라인의 전제는 **사람은 "무엇이 참인가"를 쓰고, 파이프라인이 "어떻게 생겼나"를
도출한다**는 것이다. 자세함의 축이 둘이라 하나는 깊을수록 좋고 하나는 넘어오면 안 된다.

| 축 | 예 | 판정 |
|---|---|---|
| 도메인 규칙 | 상태 전이, 금액 불변식, 권한 조건, 엣지 케이스, 장애 처리 | **깊을수록 좋다.** 파이프라인이 못 지어내는 것 |
| 해법 형태 | 테이블 컬럼·타입, 엔드포인트 경로·요청 스키마·HTTP 코드 | **쓰면 안 된다.** `data_model`·`api_spec` 노드의 산출물 |

엔티티는 **개념과 관계**로 쓴다(“한 주문에 판매자별 배송이 여럿 생긴다”). 컬럼과
타입으로 쓰면 ERD 도출 단계가 받아쓰기가 된다.

## commerce_qwen: 원본과 입력본의 차이

원본(`_reference.md`)은 Qwen에게 상세히 뽑게 한 것으로, 데이터 모델(12엔티티 컬럼표)과
API 명세(엔드포인트 40개)까지 완성돼 있었다 - 기획문서가 아니라 **설계문서**다. 그대로
넣으면 파이프라인이 도출한 게 아니라 베낀 게 되어 도출력을 잴 수 없다.

입력본은 원본에서 이렇게 바꿨다:
- **뺌**: 2번 데이터 모델(→ 개념·관계 서술로 대체), 6번 API 명세, 9번 자기 검증
  (2·6·7 상호 대조표라 근거가 사라짐)
- **손봄**: 화면 정의의 `호출 API ID` 열 제거, 본문에 남은 `API-0xx` 참조를 하는 일
  이름으로 교체(“API-012는” → “결제 생성은”), 섹션 번호 정리

**원본을 남긴 이유**: 파이프라인이 도출한 ERD·api_spec을 사람이 쓴 것과 대볼 수 있다.
지금까지 도출 품질은 눈으로 보는 게 전부였다.
