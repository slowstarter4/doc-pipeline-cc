# plan-intake: 아이디어 → 기획문서 초안

**`examples/library_plan.md`가 목표 산출물 형태의 예시다** - 제목/개요/용어
정의/섹션별 번호 목록(`1-1.`, `1-2.`...)/화면 구성/이번 범위에 넣지 않는 것.
이 스킬이 끝나면 그 구조를 가진 markdown 파일이 `examples/`에 하나 생긴다.

이 스킬은 `doc-pipeline`(LangGraph 자매 레포)의 `plan_intake` 노드와 목적은
같지만 구현은 훨씬 단순하다 - 거기는 `interrupt()`/checkpointer로 대화가
끊겼다 이어지는 걸 흉내내야 했지만, 여기는 **이 대화 세션 자체가 이미 전체
문맥을 기억**하고 있다. 별도 state 필드나 draft 누적 장치가 필요 없다 - 그냥
순서대로 물어보고, 사람 답을 세션이 계속 들고 있다가 마지막에 이 세션이
직접 markdown을 쓰면 된다.

## 절차

### 1. 6개 질문을 순서대로, 한 번에 하나씩 묻는다

자유 서술형 답이라 AskUserQuestion(객관식 도구)이 아니라 그냥 대화로 묻는다 -
질문 하나 던지고 사람 답을 받은 다음 메시지에서 다음 질문으로 넘어간다.
질문 순서·문구는 고정(LLM이 매번 새로 지어내지 않는다 - 결정적으로 할 수
있는 건 결정적으로):

1. **핵심 엔티티** - 이 시스템이 다루는 주요 데이터 대상 (예: 도서, 회원, 대출)
2. **각 엔티티의 필드** - 엔티티별로 어떤 정보를 갖는지, 필수/선택 여부
3. **주요 기능** - 각 엔티티에 대해 어떤 동작이 가능한지 (등록/조회/수정/삭제/기타)
4. **제약 규칙** - 비즈니스 로직 (예: "동시 대출 최대 5권", "연체 중이면 대출 불가")
5. **화면 구성** - 몇 개의 화면으로 나뉘는지, 각 화면에서 뭘 하는지
6. **명시적 제외 범위** - 이번엔 안 만드는 것 (로그인, 알림, 수정 기능 등)

사람 답이 부실하거나 애매하면(예: "엔티티: 아무거나") 그 자리에서 되물어도
된다 - 다음 질문으로 그냥 넘어가지 않는다.

### 2. 초안 조립

6개 답 다 모이면 이 세션이 직접(별도 도구 호출 없이) `library_plan.md`
구조를 따르는 markdown을 써낸다 - 제목, 개요, 용어 정의, 섹션별 번호 목록,
화면 구성, 이번 범위에 넣지 않는 것. **사람이 준 답에 없는 기능·제약을
지어내지 않는다** - 표현만 다듬고 구조를 갖춘다.

### 3. 최종 승인 (필수 게이트)

조립된 markdown 전체를 사람에게 보여주고 묻는다: "이대로 진행할까요? 고칠
부분 있으면 말해주세요." 사람이 수정을 요청하면 반영해서 다시 보여주고 또
묻는다 - **사람이 승인한 텍스트만 다음 단계의 ground truth가 된다.** LLM이
알아서 완성해서 밀어넣지 않는다(`build-app`/`gen-docs`가 이후 전부 이 파일
하나를 원본으로 삼으므로, 여기서 흐려지면 뒷단 전체가 흔들린다).

### 4. 저장

승인되면 파일명을 짧게 물어본다(예: "library_plan.md로 저장할까요?" - 도메인
이름에서 자연스럽게 뽑히면 기본값으로 제안, 아니면 그냥 물어본다). 승인된
텍스트 그대로 `examples/<파일명>.md`로 Write한다.

## build-app과의 연결

`build-app` 0단계에서 기획문서 경로를 못 받았거나 그 경로가 실제로는 없는
파일이면, 이 스킬을 먼저 돌려 `examples/<파일명>.md`를 만들고 그 경로를
`plan_path`로 삼아 이어서 진행한다(스택 선택 AskUserQuestion 등 나머지
0단계는 그대로).

## 이 스킬이 안 하는 것

- 스택 선택(BACKEND_TARGET 등)은 안 묻는다 - `build-app` 0단계 몫.
- `requirements`/`screen_design` 등 뒷단 문서는 안 만든다 - `gen-docs` 몫.
  이 스킬은 오직 `plan_doc`(기획문서 원본) 하나만 만든다.
