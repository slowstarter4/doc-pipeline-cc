# 계약 이의제기(objections) 프로토콜 — Level 1

`gen-backend-*`/`gen-frontend-*` 모든 스킬이 디스패치 프롬프트에 이 문서를
참조로 넣는다. 스택 무관 공통 규칙이라 여기 한 곳에 둔다 - 스택별
`gotchas.md`처럼 복제하면 문구 하나 고칠 때마다 N곳을 고쳐야 한다.

## 목적

협상 기계장치가 아니다. 계약(`api_spec`)에 정보가 없거나 모호해서 임의
판단을 내린 지점을 **기록**만 한다. 판정도 재디스패치도 여기서 안 한다 -
오케스트레이터가 모아서 사람에게 보여줄 뿐이다.

**정적으로 검사 가능한 건 이 메커니즘을 쓰지 않는다.** 명세에 없는
경로/method 호출, 응답 wrapper key·구조분해 키 불일치는 `verify-frontend`
스킬(`scripts/verify_frontend.py`)이 이미 결정적으로 잡는다. 여기서 다루는
건 오직 "구현해보니 계약에 정보가 부족하더라"뿐이다.

## 언제 남기나

**남길 것:**
- 화면설계서/요구사항에 있는 걸 구현하려는데 계약에 대응하는 엔드포인트나
  필드가 없을 때
- 계약에 여러 해석이 가능해서 한쪽으로 정했을 때
- 에러 응답 형식처럼 계약에 안 적혔는데 구현엔 필요한 것을 임의로 정했을 때

**남기지 말 것:**
- 계약에 명시된 대로 구현했는데 개인적으로 다른 설계가 낫다고 생각하는 것
  (취향 차이는 이의가 아니다)
- 스택 관련 기술적 어려움 (그건 각 스킬의 `gotchas.md` 영역)

이의를 남긴다고 작업을 멈추지 않는다 - 코드는 일단 최선의 판단으로 완성한다.

## 어디에, 어떤 형식으로

파일: `generated/objections/<slice>.json` (`<slice>`는 이 서브에이전트가
맡은 도메인 조각명 — 백엔드는 `endpoint_groups.py`가 나눈 조각명, 프론트는
화면명 또는 전체를 한 서브에이전트가 맡는 스택이면 `frontend`).

**이 파일은 이 서브에이전트 혼자 소유한다.** 병렬로 뜨는 다른 조각의
서브에이전트는 각자 다른 파일에 쓰므로 동시 쓰기 충돌이 없다 - 락이나 재시도
로직 필요 없음. 파일이 이미 있으면(재시도로 같은 조각이 다시 도는 경우)
**덮어쓴다** - append하지 않는다. 이전 시도의 이의는 이번 구현과 대응이
안 맞을 수 있어 무효로 본다.

이의가 하나도 없으면 파일 자체를 만들지 않는다 (빈 배열 파일을 굳이 남길
필요 없음 - 오케스트레이터의 `collect_objections.py`가 파일 없음 = 이의
없음으로 처리한다).

배열 안 각 항목:

```json
{
  "from": "frontend",
  "slice": "loans",
  "severity": "blocking",
  "issue": "GET /loans 응답에 회원 이름이 없어 화면설계서의 '회원명' 컬럼을 채울 수 없음",
  "assumed": "memberId를 그대로 표시했음",
  "suggestion": "응답에 memberName 추가, 또는 프론트가 GET /members를 따로 호출"
}
```

- `from`: `backend` | `frontend`
- `slice`: 이 서브에이전트가 맡은 조각명 (파일명과 동일해야 함)
- `severity`:
  - `blocking` — 계약대로면 화면설계서/기획문서의 요구를 아예 구현 불가
  - `workaround` — 임의 판단으로 우회해서 구현은 했음
  - `question` — 모호해서 한쪽으로 해석했음, 확인 필요
- `issue`: 계약의 어느 부분이 부족한지
- `assumed`: 그래서 어떻게 처리했는지 (없으면 `null`)
- `suggestion`: 어떻게 고치면 좋을지 (구현자 관점 제안, 강제 아님. 없으면 `null`)

`from`/`slice`/`severity`/`issue`는 필수 - 없으면 `collect_objections.py`가
그 항목을 조용히 건너뛴다(경고만 남김).
